# 계정 저장·동기화·삭제

0.4 개발 변경. 프로필·꾸미기 동기화는 **기본 꺼짐**, 계정별·기기별 선택이다. 켜면 서버 프로필을 불러오며 이후 저장부터 Supabase Auth 메타데이터를 갱신한다. 끄면 이후 변경은 기기에만 남는다. 끄기 자체가 기존 서버 프로필을 삭제하지는 않는다.

프로필은 `account/profiles.enc`에 OS 암호화로 보관한다(최근 16개 계정). 로그인 유지를 사용자가 선택하면 `account/session.enc`에 사용자 ID·이메일·갱신 토큰만 저장한다. 접근 토큰·비밀번호는 저장하지 않는다. 시작 시 Supabase에 갱신을 요청해 동일한 사용자 ID/이메일인지 다시 검증한다. OS 암호화를 사용할 수 없으면 로그인 유지가 꺼지고 프로필은 메모리에서만 적용된다. 로컬 프로필은 브라우저 쿠키를 계정별로 분리하는 기능이 아니다.

0.5의 `tasks.enc`는 최대 100개 AI 작업의 상태·시간·승인 origin·고정 오류 코드·동작 결과만 보관한다. 목표·본문·입력값·API 키는 저장하지 않는다. `window-tabs-1.enc`부터 `window-tabs-8.enc`는 분리 창의 URL/그룹 복구 파일이다. 두 종류 모두 같은 OS 사용자 프로필에 속하며 Supabase 동기화·로그아웃·계정 삭제의 원격 삭제 대상이 아니다. OS 보호 저장소가 없으면 RAM에서만 동작한다. 앱 제거는 기존 방침대로 사용자 프로필을 보존한다.

로그아웃은 메모리와 저장된 갱신 토큰을 지우고 서버의 `scope=local` 세션 해제를 요청한다. 다른 기기 로그아웃은 계정에 묶인 네이티브 확인 후 `scope=others`를 요청한다. 이미 발급된 JWT는 만료까지 유효할 수 있다. 기기별 상세 세션 목록 API는 연결하지 않았다.

## 계정 삭제 서버 산출물 — 배포되지 않음

`supabase/functions/delete-account`는 서버 전용 구현과 로컬 HTTP fixture 테스트를 포함한다. 앱에는 관리자 키가 없으며 아직 삭제 버튼/API를 활성화하지 않았다. 실제 사용자나 데이터는 삭제하지 않았다.

삭제 처리:

1. JSON POST·Bearer 인증·명시적 `DELETE` 확인과 현재 비밀번호를 요구한다. 브라우저 Origin 요청을 허용하지 않는다.
2. 고정된 프로젝트의 `/auth/v1/user`에 토큰을 검증받는다. 요청 본문에서 사용자 ID를 받지 않는다.
3. 서버가 확인한 이메일과 현재 비밀번호로 재인증하고 ID가 같은지 확인한다. 이 경로는 현재 이메일/비밀번호 계정용이다.
4. 서버 전용 service-role로 **그 사용자만** 삭제한다. Auth 메타데이터와 FK cascade 대상 행이 삭제된다. 임시 재인증 세션은 종료한다.
5. 오류는 상세 토큰·비밀번호·원문 API 응답 없이 반환한다. 성공을 확인하지 못하면 성공이라고 표시하지 않는다.

동봉 SQL은 향후 별도 환경설정 테이블을 사용할 경우의 RLS·소유자 정책·Auth 사용자 삭제 cascade 기반이다. 현재 앱은 이 테이블을 사용하지 않으며 **실제 Postgres/Supabase 적용은 미검증**이다. 서비스 계정의 RLS 우회 권한은 서버 삭제 함수에만 속한다.

실제 배포 전 프로젝트의 연결 테이블·Storage 객체·백업 보존 정책을 점검하고 삭제 범위를 확정해야 한다. 현재 앱은 Supabase Storage에 파일이나 브라우저 기록을 올리지 않는다. 향후 추가된다면 삭제 구현을 같이 확장한다. Auth 삭제는 로컬 북마크·방문 기록·웹사이트 쿠키·API 키까지 원격으로 지우는 기능이 아니다. 로컬 데이터 삭제는 기존 관리 화면의 별도 확인 절차를 사용한다.

## 검증 범위

단위 테스트는 opt-in 이전 프로필 요청 없음, 계정 바인딩, 지연 갱신과 로그아웃 경쟁, OS 암호화 실패 시 평문 저장 없음, 삭제 함수의 다른 사용자 지정·재인증 실패·서버 실패를 검증한다. 실제 서비스의 메일·로그인 유지 재시작·다른 기기 세션 해제·계정 삭제는 이번에 실행하지 않았다.
